Testing stale-worker fencing and recovery in Valkey-backed agent workflows.

Worker A starts an agent task, records checkpoint version 12, and calls an external tool. Its lease then expires. A coordinator transfers ownership to worker B, which advances the task. Minutes later, A resumes with version 12 still in memory and tries to publish its result.

Serverless workers are especially exposed to this pattern: request deadlines, frozen instances, retries, asynchronous tool calls, and rapid scale-out can separate a worker's lifetime from the lifetime of its lease. A reconnect burst can bring several delayed workers back at once, but reconnecting successfully does not make their state authoritative.

The protocol is not specific to artificial intelligence (AI); it applies to any leased workflow runner. Agent systems make the failure especially visible because model inference and external tool calls can outlive the serverless invocation that initiated them.

That write can reach Valkey even though A no longer owns the task. Command success is therefore the wrong correctness test. The real question is whether the write is still a valid workflow transition—and whether an accepted transition survives the recovery contract the application claims to provide.

This investigation contributes a testable checkpoint-transition contract for Valkey-backed workflows, an atomic owner-epoch-and-version protocol, and a reproducible method for verifying stale-worker rejection and recovery of acknowledged progress.

Valkey's agent-memory guidance covers the broader landscape. This post tests a narrower question: how do we prove that a distributed worker's checkpoint update is still authoritative?

A successful command can still corrupt workflow state

Begin with the implementation that does not fence anything.

Worker B takes ownership at epoch 43 and publishes version 13 with checkpoint reference B. Worker A later submits the transition it prepared at epoch 42/version 12. An unconditional publication accepts A's command and writes version 13 with checkpoint reference A.

The command succeeds. The workflow state is wrong.

In the final batch, this sequence was reproduced in 30/30 measured runs. The raw response was OK, the stored version remained 13, and the authoritative reference changed from B's payload to A's stale payload.

Ownership fencing and checkpoint versions answer different questions

Each workflow hash contains:

owner: the worker expected to publish;

epoch: a fencing generation incremented during takeover;

version: the accepted checkpoint sequence;

transition_id: the latest logical transition identifier;

checkpoint_ref: an immutable content-addressed payload reference.

The owner and epoch establish an ownership precondition. The version establishes a checkpoint-ordering precondition.

A version check alone rejects a late write only after another transition has advanced the version. Immediately after takeover, version 12 may still be current, so stale worker A can pass a version-only comparison.

An owner-and-epoch check alone rejects former owners, but two operations from worker B can both carry owner B and epoch 43. Without a version comparison, both can succeed and the second can overwrite the first.

The central claim tested here is that ownership fencing and version sequencing are independent checks. This workflow requires both.

The expected_owner value is a consistency assertion, not authenticated caller identity. A hostile caller could claim another owner unless the application binds worker identity to credentials or an unforgeable capability. This experiment makes no authentication claim.

The complete transition contract

Valkey Functions execute the read-check-write sequence atomically on the server handling the key. The experiment uses one takeover Function and four checkpoint variants.

The complete checkpoint Function receives the same fields as every negative control:

advance_checkpoint(expected_owner, expected_epoch, expected_version,
                   transition_id, checkpoint_ref)

Its admission order is:

reject malformed transition metadata

if stored epoch != expected_epoch:
  return STALE_EPOCH

if stored owner != expected_owner:
  return OWNER_MISMATCH

if latest transition_id == submitted transition_id
   and stored version == expected_version + 1:
  if stored checkpoint_ref != submitted checkpoint_ref:
    return TRANSITION_PAYLOAD_CONFLICT
  return ALREADY_APPLIED

if stored version != expected_version:
  return VERSION_CONFLICT

set version = expected_version + 1
set transition_id and checkpoint_ref
return OK

The transition_id is therefore bound to the complete content-addressed checkpoint_ref. An identical retry returns ALREADY_APPLIED only while the submitted owner and epoch remain current and that transition is still the latest saved transition. Reusing the ID with another payload reference returns TRANSITION_PAYLOAD_CONFLICT and leaves the accepted state unchanged.

This guarantee covers only the latest saved transition ID. Detecting an older retry after a newer transition replaces it requires a retained journal or another authoritative reconciliation record.

The surrounding coordinator or another durable authority must prevent fencing-epoch reuse and rollback. The Function compares the submitted epoch with the stored value; it cannot independently detect that the stored ownership record itself has regressed. If recovery exposes an older record, checkpoint admission must stop until the authoritative coordinator restores safe ownership.

Three controlled scenarios distinguish the mechanisms

The harness runs every scenario against every variant.

Scenario A — stale A after B commits. B has already advanced version 12 to 13. A then submits its epoch-42/version-12 transition. This shows the unconditional overwrite and confirms that a version comparison can reject this particular late ordering.

Scenario B — stale A before B commits. Ownership is now B/epoch 43, but the checkpoint is still version 12. A submits its epoch-42 transition before B advances. This is the case that proves version-only checking is insufficient.

Scenario C — competing writes from the current owner. Two operations from B carry owner B, epoch 43, and expected version 12, but publish different transitions. This is the case that proves owner-and-epoch checking alone is insufficient.

The harness records evidence at three levels:

Server execution: submitted fields, raw Valkey response or error, and command duration.

Application correctness: final owner, epoch, version, transition ID, checkpoint reference, and reference resolution.

Recoverability: the same contract state and payload reference after the injected primary loss.

A passing negative-control cell means that the expected unsafe behavior was reproduced. It does not mean that the incomplete variant is safe.

Reproducible method

Aditi Gupta and Shuva Jyoti Kar jointly designed the protocol and harness. Shuva Jyoti Kar ran the final batch on macOS-26.3.1-arm64-arm-64bit-Mach-O on 2026-11-03.

After five discarded warm-ups, 30 measured trials each started from clean Compose containers and volumes. On the same-host primary-replica topology, every trial ran 12 contrast cells, six complete-protocol checks, 10,000 independent task-key transitions, and 100 auditable transitions before primary loss. The lab did not exercise Valkey Cluster, resharding, or cross-key atomicity.

Keep external effects outside the atomicity claim

The production contract assumes that the checkpoint payload lives outside Valkey in an immutable, content-addressed object store. In the harness, a local content-addressed filesystem directory is the test double for that store. It validates reference publication, replay binding, orphan detection, and checksum resolution inside the lab; it does not test an external store's availability or durability. No Valkey Function atomically commits Valkey and an external payload store.

An object written before a rejected metadata transition is an orphan, not an accepted checkpoint. Cleanup must wait until the application knows that no authoritative request can still publish that reference.

An external tool call is another independent boundary. If a worker provisions a resource before losing ownership, rejecting its checkpoint does not undo the side effect. The tool operation still needs its own idempotency key, status query, or reconciliation record.

What these results do—and do not—show

These same-host development measurements describe one primary and one replica, not universal Valkey performance limits. They do not cover clustered keys, resharding, multi-primary operation, cross-key transactions, or restored redundancy after promotion.

The owner check enforces workflow consistency, not cryptographic caller identity; malicious identity claims remain out of scope. The experiment also does not benchmark connection storms, connection pools, or backoff. Its narrower serverless result is that a reconnecting worker must re-prove its owner, epoch, and version.

The failover evidence covers primary loss, replica promotion, accepted-state audit, and one successful post-promotion transition. Thirty clean-start runs with no unexpected result support only “no violations observed”; they neither prove impossibility nor establish a stable failover-tail percentile.

Practical takeaways

Do not equate command success with workflow correctness. The blind-write control can return OK while installing a stale payload.

Keep ownership fencing and checkpoint sequencing separate. Owner plus epoch excludes former owners; version comparison serializes current-owner transitions.

Bind retries to payload identity. A transition ID alone is not enough when the same ID can arrive with different content.

Audit acknowledged state after the failure you claim to tolerate. An acknowledgment policy is an input to the recovery contract, not proof of survival.

Treat external side effects as separate transactions. Checkpoint fencing cannot undo an already-executed tool action.

Valkey Functions provide the atomic building block for this protocol. The stronger result comes from the experiment around that Function: reproduce the failure without each guard, verify the complete contract, and then count only the acknowledged transitions that remain correct after recovery.

Run the companion harness against your own checkpoint contract before treating successful commands as durable workflow progress.
